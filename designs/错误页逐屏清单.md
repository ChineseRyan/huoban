## 正文里写实现术语

- **现状**：正文（`#e-body`）里出现「pywebview 的桥没有注入成功……如果反复出现，说明打包缺了 webview 的 hooks」；
  另有一条正文写「job_poll 返回了空值。」，标题写「轮询出错」、「后端没有回应」，还有两处正文写「后端返回了空的结果。」。
- **问题**：这些只有维护者看得懂，而且它们就摆在正文，不在「技术细节」里。用户出事的这一刻要的是「我该做什么」，
  不是「哪一层断了」。
- **建议**：正文只留能照做的动作（重启程序 / 再拖一次），术语进 `opts.detail`；标题改人话：
  「轮询出错」→「和后台失去联系」，「后端没有回应」→「后台没有回应」。
- **判词（2026-11-17）**：改。

## 原始异常直接进正文

- **现状**：`showError(..., String(err), ...)` 把异常原样放进正文 —— 三处 catch 分支这样做：
  「打不开文件选择框」「打不开复核页」「打不开这本书」。
- **问题**：用户看到的是英文堆栈；正文还可选中复制，容易被当成「要我去解决」。
- **建议**：正文写一句人话，`String(err)` 进 `opts.detail`。
- **判词（2026-11-17）**：改。

## 技术细节展开后的裁切与双层滚动

- **现状**：720×520 档、正文三段 + 展开「技术细节」时，`.scroll` 可视高 318、内容高 372，
  多出 54px 要滚；同时 `pre` 自己还带 `max-height` 与 `overflow: auto`。
  展开态里技术细节的最后一行正好压在出口分隔线上。
- **问题**：两个滚动条叠在一起，用户不知道该滚哪一个；被压在分隔线下的那截看着像被裁掉。
- **建议**：矮窗媒体查询里去掉 `pre` 的 `max-height`，只留外层一层滚动。
- **判词（2026-11-17）**：改（按建议）。

## 技术细节灰框与正文左边缘不齐

- **现状**：1013×580 实测 `pre` 左边缘 197、正文左边缘 217 —— 差 20px，正好是 2px 印色竖线 + 18px 间距。
- **问题**：灰框比它上面的正文往左塌出去一块，看着像没对齐（正文被竖线推右，灰框没被推）。
- **建议**：`.err-more` 补 `margin-left: 20px` 与正文对齐；或者反过来认定「附录块占满整行」并写进注释。
- **判词（2026-11-17）**：改（按前者）。

## 三颗出口的层级倒挂

- **现状**：最坏态三颗出口 —— 「换一个文件」132×46 主按钮、「仍然继续」51×20 虚线小字、
  「打开所在目录」76×20 虚线小字，右对齐竖排（占 397–506）。
- **问题**：「仍然继续」是这屏唯一会改结果的动作（明知整本只有一行还要做），却和「只是看一眼」的
  「打开所在目录」同在最轻一档 —— 后果最重的看起来最轻。
- **建议**：A. 把「仍然继续」提一档成描边按钮（与「回上一步」同档），并和「打开所在目录」拉开一档间距；
  B. 维持现状，靠正文里那句「也可以仍然继续」解释。
- **判词（2026-11-17）**：按 **A**。

## 页码条与引文块的对齐

- **现状**：720×520 下页码条左边缘 48、标题文字左边缘 68；页码跟着 2px 红线对齐，跟文字不对齐。
- **问题**：红线只有 2px，远看等于「没对齐」。
- **建议**：倾向不动（红线就是引文块的左边缘）；若要更整齐，给页码条补 20px。
- **判词（2026-11-17）**：**不改**。

## 正文段间距偏大

- **现状**（落地前实测，真实糊行文案 + 技术细节展开）：标题与正文 **10px**；正文段落之间
  **25 / 26 / 26px**（三段合计 77px，因为正文是 `white-space: pre-wrap`，段间靠一个空行撑开，
  行高 22.95px）；正文到「技术细节」**18px**（矮窗媒体查询）。
  可滚高度：720×520 **73px**、1013×580 **13px**。
- **问题**：一屏里最贵的那点竖向空间被三个空行吃掉；长文案在 720×520 上一进来就要滚。
- **建议**：两档 ——
  - 甲（只收外边距）：标题下 10→6、技术细节 18→12（矮窗）。段间不动，720 可滚 73→63。
  - 乙（甲 + 正文按空行拆段）：段间交给 CSS，25–26 → **12px**。720 可滚 →30、1013 →0。
- **判词（2026-11-17）**：按 **乙**（拆分段落，段距 12px）。
- **落地（2026-11-17）**：`showError()` 改用 `errBody()` 把正文按空行拆成 `<p class="err-p">`，
  段距与段内换行都由 CSS 定（`.err-body .err-p { margin: 0 0 12px; white-space: pre-wrap; }`）；
  标题下 6px、正文到技术细节 16px（矮窗 12px）。走真实错误路径实测（`_shot/err_landed.js`）：
  四段、段距 12/12/12、标题下 6、正文到技术细节 12（矮窗），**720×520 与 1013×580 展开态都可滚 0**。
- **验收图**：`_shot/land-720-light.png`、`_shot/land-720-dark.png`、
  `_shot/land-1013-light.png`、`_shot/land-1013-dark.png`；候选期前后对比见
  `_shot/sp-cur-*` 与 `_shot/sp-yin-*`、`_shot/sp-jia-*`、`_shot/sp-yi-*`。

## 核过、不算问题的两条

- **页码显示「00 出问题了」**：`showError()` 在 `step` 缺省时把页码写成 `00`。核过 `gui/ui.html` 里
  `showError(` 共出现 31 次，其中一处是函数定义、其余 30 次调用**每一处都给了 `step`**，
  真机走不到这支兜底 —— 不作为问题上报。
- **底部留白 14px**：出口条底边 506、视口 520，余 14px。核过这是**全站各屏一致**（④ 元数据页的出口条同样止于 506），
  不是出错页的毛病，改它要动公共骨架 —— 与这一屏无关。

## 证据

- **量法**：临时脚本 `_shot/shot_error.js`（不入库）用 CDP 把真 `gui/ui.html` 切到 `#view-error`，
  按三种代表态填内容：短文案（标题 + 一行正文 + 一颗出口）、长文案（三段正文 + 技术细节收起 + 两个出口）、
  最坏态（长文案 + 技术细节展开 + 三颗出口）。只改 DOM 的显隐与文案，等价于 `showError()` 那一段干的事。
- **截图**：`_shot/err-short-1013.png`（1013×580 浅色，短文案）、`_shot/err-long-720.png`（720×520 浅色，长文案）、
  `_shot/err-worst-720.png`（720×520 浅色，最坏态）、`_shot/err-worst-720-dark.png`（720×520 深色，最坏态）。
  这四张是清单期的取证；落地后的对照图另出。
- **关键数字**：720×520 最坏态 `scrollable = 54`（318 可视 / 372 内容）；1013×580 最坏态 `scrollable = 0`；
  灰框与正文左边缘差 20px；三颗出口尺寸 132×46 / 51×20 / 76×20。
- **文案是否被测试钉住**：清单期核过 `tests/test_gui.py` 里没有断言出错页这几句文案，改文案不连带红。
