## 1. 目标与边界

**一句话**：拖进一个脏 TXT → 出 EPUB。中途可以只点一个按钮，也可以细看每一处改动。

| 决策 | 结论 | 依据 |
|---|---|---|
| 壳 | pywebview 6.2.1 + WebView2 + 单文件 HTML | WebView2 Runtime 本机实测在 `C:/Program Files (x86)/Microsoft/EdgeWebView/Application/`（2026-10-28 时是 155.0.4283.62，2026-11-06 复核已有 156.0.4314.50 / 156.0.4314.58 —— **版本号随 Edge 更新漂移，别把具体版本当常量**）；Python 同进程直调，无 HTTP、无临时文件 |
| 前端 | 一个 HTML，零构建、零 npm | 不引 Node 工具链，保持零依赖；换视图只切 class |
| 导入格式 | TXT 与 EPUB 两条入口，共用同一条产线（§12） | EPUB 难在容错而非猜：章节边界由 OPF spine + nav/NCX 白送，编码由 XHTML 自带声明，目录块与广告行基本不存在 |
| 批量 | 先单本闭环，UI 留「加入队列」占位 | 队列的并发/失败隔离/命名冲突是三件新复杂度；`clean_file(path)` 单文件入口天然可复用 |
| 复核 | **保护行重跑**（§7） | 决策落在「行」这一层：`model.Paragraph` 只有 `{text, kind}` 不记行号，被删的行根本不在章节树里，段落级编辑接不回清洗层 |
| 复核范围 | **只放开「删除」与「合并」两类** | 这两类在报告里都带原始行号，语义就是「这一行别动」；修复类（标点归一/零宽/缩进）逐条勾等于重做规则，收益极低 |
| 封面 | Pillow 位图海报：九款版式 × 六套配色，`sha256(书名)` 自动挑，可「换一个」 | 原型已跑通并全量验证（§8.8）；Calibre 那套已作废（§8.1） |
| 产物目录 | 写在输入文件旁 `<书名>_gui/` | 书和产物待在一起，换盘时跟着书走；与 CLI 的 `<名>_clean/` 不撞名 |
| 分发 | PyInstaller onedir | 不追求单文件启动速度；`webview/__pyinstaller` 自带 hooks |

**明确不做**：多语言界面、在线更新、自由调色板（只让挑 6 套预设）、字体浏览器、EPUB 内正文编辑、AI 生图封面（Calibre 那个 &AI Generate 是另一套东西，`basic_widgets.py:1311-1313`）。这条说的是**产品不做生图功能**，不涉及素材来源 —— §8.10 那九张整幅底图本身就是 AI 生成的。

## 2. 为什么是 pywebview

选型的分水岭只有一条：**文件拖放能不能拿到绝对路径。**

1. **pywebview 已实装**（读 `site-packages/webview` 源码确认，非文档印象）：`platforms/edgechromium.py:229-241`
   在 WebView2 原生 `FilesDropped` 回调里取 `CoreWebView2File` → 存进 `dom/__init__.py:49` 的
   `_dnd_state`（`{"num_listeners": 0, "paths": []}`）；`util.py:288-300` 按 basename（`urllib.parse.unquote`）
   匹配后注入 `event.dataTransfer.files[i]` 的 `pywebviewFullPath` 字段，再 `Thread(target=handler).start()`。
   → 前端 drop，Python 端事件对象里直接有绝对路径。
2. **DOM 事件回调在独立线程**（`util.py:303`），不阻塞 UI 线程；`js_api` 每次调用同样 `Thread(target=_call)`
   （`util.py:335`）。
3. **Tauri v2 拿不到同样便利**：`onDragDropEvent` 只给路径字符串数组且需宿主额外配置，本机又无 Rust 工具链。
   为一个壳引 Rust + 前端构建链，不值。

代价（诚实列出）：

- **单窗口**：Windows 后端多窗口不稳 → 复核界面用覆盖层/抽屉，不开子窗。
- **标题栏加载期闪烁**：`create_window` 内部 `events.shown.wait(15)` / `loaded.wait(15)` → 启动先 load 一张骨架屏。
- 界面字体靠系统回退（WebView2 自理）；EPUB 内嵌字体是 `fonts.py` 的事，与 GUI 无关。

## 3. 三个实现陷阱（只有读源码才会发现）

| 陷阱 | 源码证据 | 对策 |
|---|---|---|
| drop 必须**由 Python 端注册**且要 prevent_default | `dom/element.py:412` 只有 `Element.on(那个事件名)` 才让 `_dnd_state` 的 `num_listeners` 加一（`off` 见 `:440`）；`element.py:373` 传裸 callback 时不注入 `e.preventDefault()`，浏览器默认行为会把窗口直接导航到该文件 | 注册 `DOMEventHandler(cb, prevent_default=True)`（`dom/__init__.py:13`，签名 `callback, prevent_default, stop_propagation, stop_immediate_propagation, debounce`）；HTML 里 `dragover` 也要 preventDefault，否则没有放置光标 |
| 二次 `load_html` 会**弄丢拖放监听** | `dom/dom.py:19` 的 `__on_loaded` 每次 loaded 事件把 `self._elements` 清空，注册过监听的元素表就空了 | 启动只 load 一次；后续换视图全部用 `run_js` 切 class，绝不 reload |
| 多文件同名 basename 会**配错路径** | `util.py:291-300` 按 unquote 后的文件名匹配并 remove，同名两个文件必有一个配错 | 本期只接**一个**文件（正好与「先单本」一致）；将来批量要么一次一本，要么走文件选择器多选 |

- **②的警告不可折叠**：AGENTS.md 铁律 2「先报告后动手」，一键式不能等于把账单藏起来。
- ③ 的行展示沿用 `cleanreport.py` 口径（`SAMPLE_LIMIT=8`、截断 `_TEXT_LIMIT=60`），并复用 `redact.shape()`
  的形状描述（`〔长N 中N 西N 空N 符N #指纹〕`）作为**不复制正文**的行标识；要看原文就点行号回本地文件。
  这与 `redact.py` 的立场一致：AI 只看元数据，原文核对留在本地人眼。
- ③ 重跑后回到 ②（数字会变），**调整不丢**：adjust 累积在当前会话里，可逐条撤销。
- **② 页有两套账单，按 `payload.kind` 分支**（两条入口共用产线，但不是同一件事）：
  TXT 是「字数 · 章数 · 删行 · 合并」，明细给编码置信度/删除/改写/碎行/硬折行；
  EPUB 是「字数 · 章数 · 图 · 卷」，明细给版本/目录条目/段落/图片分流/分片/续接/章前/附带。
  **导入的书不给"编码置信度"**（XHTML 自带声明，不存在猜错），
  **也不给"删了多少行"**（它没经过清洗，硬塞一堆 0 会让用户以为清洗跑了却一无所获）。
  相应地 ② 页两个按钮换措辞：「打开导入报告」（导入没有 clean-report.md，报告是 report.json）、
  「检查清洗结果」**置灰**（没有可复核的删除/合并）—— 禁掉而不是隐藏，按钮位置跳来跳去比灰着更让人困惑。

```
    report.json       导入报告（epubread 的 report dict），**没有 clean-report.md**
    images/           带回的插图，打包时按 image_dir 塞回包里
    死灵之书.epub
```

目录名从 `<文件名>_gui` 改成 `<书名>_gui` 是靠**一次整目录 rename**（图片在解析过程中就落盘了，
那时书名还不知道）。rename 失败或目标已存在时退回 `<文件名>_gui` ——
宁可目录叫文件名，也不把两份产物混进一个目录。

三条硬约束（全部从 CLI 继承）：

1. **永不写输入文件**：沿用 `cli._write_epub_output` 的做法，用 `os.path.samefile`（不是 `resolve()`，
   硬链接也要算）在写盘层拒绝「输出 == 输入」。
2. **可复现**：`write_epub(modified=<输入 mtime>)`，与 CLI 默认一致。GUI **不加**「用当前时间」开关，
   否则同一本书 GUI 与 CLI 会产出不同的包。
3. **目录可整体换盘**：设置里留一个「产物根目录」覆盖项（默认跟随输入文件）。

## 7. adjust 接口 —— 已实现（2026-10-26）

> 变更记录：本节原本写的是「现状：没有任何保护入口」+「提议的形状」。2026-10-26 已按下面的契约
> 实装到 `huoban/clean.py`，并补了 CLI 与测试。**实际形状与最初提议有两处不同**，都记在下面
> 「与提议的差异」里，GUI 按本节写就行，不用再看历史版本。

### 7.1 入口

```python
clean_text(text, *, ..., adjust: dict | None = None) -> CleanResult
clean_bytes(raw, *, source="", adjust=None) -> CleanResult
clean_file(path, *, adjust=None) -> CleanResult
```

CLI：`clean` 与 `epub` 两个子命令都有 `--adjust`，值是 **JSON 文本**（以 `{` 或 `[` 开头）
或**装着 JSON 的文件路径**（其余一律当路径）。复核界面把勾选状态写成临时文件丢过来，
人手工试一条时直接贴 JSON。`[1,2]` 这种"想贴 JSON 但贴错了形状"也按 JSON 处理，
报「应该是 JSON 对象，实际是 list」，不会误导成"读不到文件"。

```bash
python -m huoban clean 书.txt --adjust '{"protect_lines": [1024, 1051]}'
python -m huoban clean 书.txt --adjust adj.json
python -m huoban epub  书.txt --adjust adj.json -o out/
```

`epub --book-json` 时 `--adjust` 无效（那一步跳过清洗），会打一行提示说明，不静默吞掉。

**失败一律同一个出口**：读不到文件、不是合法 JSON、不是 JSON 对象、以及清洗层的形状错，
全部兜成一行 `人工调整有问题：…` + **返回码 2**，不给 traceback。文件读失败不再走另一套
文案与返回码 1 —— 复核界面只需要认一种失败形态。

### 7.2 输入形状

```python
adjust = {
    "protect_lines":  [1024, 1051],   # 原始 1 基行号：不许当整行广告/目录删除
    "protect_ranges": [[200, 240]],   # **闭区间**，同义（框选一片时用）
    "merge_breaks":   [1052],         # 强制在该行之前断开碎行合并
}
```

- 行号一律是**清洗前原文的 1 基行号**，与 `book.json` 里 `Chapter.start_line`、
  报告里 `samples[].line`、`dropped_lines[].line` 同一口径。
- `merge_breaks` 只在"这一行本来会被并进上一段"时才起作用；本来就不会合并的行
  指定了也白指定（`merge_breaks_hit` 只数真的拦住的那几次）。
- 保护的语义是**"这一行的文字别删"**，不是"把它升成标题"。三类受保护行落地方式不同：
  - **整行广告**：以**独立一段**留在书里（`entry` 非空让并碎行跳过它）。整行广告没有
    可切的正文前缀，硬焊进上一段只会把段落弄脏。
  - **目录标记行**（`目录` / `目次` / `目录：`）：降级成**普通正文行**。这类行同时落在
    前言类标题家族里（`_FRONT_BACK_WORDS` 含「目录」），不清掉标题标记就会凭空多出一个
    空章节「目录」挂进书里 —— 而删它的那条规则本来就在说"这不是标题、是标记"。
  - **目录块里的条目行**（受保护后不再删）：同样降级成普通正文行，且**各自独立成段**
    （`_Line.frozen`）。两条理由：目录条目带页码尾巴，当标题用会凭空多出假章节；相邻条目
    又短又没句末标点，正是并碎行最爱焊的形态，焊起来用户就分不清哪一行是哪一条了。
  - **带行内广告的正文行**：整行原样保留，**尾巴不切**（`inline_ad_cut_lines` 不计这一行）。
    行内切除本来就不删行，所以它不出现在 `dropped_lines` 里 —— 如果 `protect_lines` 也不管它，
    用户就没有任何入口能救回这一行（复核界面是拿 `dropped_lines` 勾选的）。

### 7.3 两类错误，两种处理（这条是实装时才定下来的）

| 错在哪 | 处理 | 为什么 |
|---|---|---|
| **结构**：不是 dict / 有不认识的键 / `protect_lines` 等三个字段不是列表（**`null`、`0`、`""`、`false`、`{}` 也算**） / `protect_ranges` 的某一项不是 `[起, 止]` 两元组 | 抛 `ValueError` | 键名和形状是调用方与清洗层的契约，写错了说明两边对不上。猜着执行会变成"用户以为保护了 A、程序保护了 B"，报告上看不出来。**假值尤其要挡**：`{"protect_lines": null}` 和 `{"protect_lines": [3]}` 差一个字符，静默当空列表等于"用户以为保护了、程序什么都没做" |
| **行号数据**：越界 / 不是整数 / bool / 区间起点大于终点 / 区间元素不是整数 | 忽略该项，记进 `report["adjust"]["ignored"]`，并升一条 warning | 换一本书、或原文改过，行号必然对不上，这是可预期的日常情况，抛异常等于让界面卡死。但**绝不静默** |

**给了行号却没命中**的，逐行点名，不只报总数：

```python
report["adjust"]["unmatched"] = {
    "protect_lines": [5],     # 给了"保护第 5 行"，但第 5 行没有任何可保护的东西
    "merge_breaks": [],       # 给了"断开第 7 行"，但那行本来就不合并
}
```

这一项配一条 warning 升出去。**「没命中」不等于「行号算错了」**——两种情形在这一层分不开：
1. 行号对不上这份原文（换书、原文改过）——行号只对本次输入有效；
2. 行号对得上，但那一行本来就不会被删/被并（正文里的普通句子）。

所以文案只陈述事实（"没有对应的可改动位置"），不猜原因。早先只在"一条都没命中"时
报警、且文案写死"可能不是按当前原文算的"，对第 2 种是**误诊**，而且部分命中时
（要 3 行、只保住 1 行）连提示都没有，用户会以为 3 行都保住了。

CLI 侧把 `ValueError` 兜成一行 `人工调整有问题：…` 并返回码 2，不给 traceback。

### 7.4 报告形状（实际）

`report` 新增两个顶层键：

```python
report["dropped_lines"] = [
    # 全量清单，**不受 samples 的 8 条上限约束**，按 (line, kind) 排序
    {"line": 1024, "kind": "ad", "protected": False, "text": "（前 60 字）"},
    {"line": 1051, "kind": "toc", "protected": True,  "text": "（前 60 字）"},
]

report["adjust"] = {
    "applied": {                      # 实际生效的，界面据此把勾选态画回去
        "protect_lines": [1024, 1051],
        "merge_breaks": [1052],
        "protect_count": 2,
    },
    "requested": {"protect": 2, "merge_breaks": 1},   # 用户要了几个（含没生效的）
    "protected": {"ad": 1, "toc": 1, "inline": 0, "lines": 2},  # 保护住没删的行，按类别
    "merge_breaks_hit": 1,                            # 真的拦住了一次合并
    "unmatched": {                                    # 给了行号、那儿却没事可做（逐行点名）
        "protect_lines": [],
        "merge_breaks": [],
    },
    "ignored": [{"field": "protect_lines", "line": 9999,
                 "reason": "越界（本次输入共 5000 行）"}],
}
```

`protected.lines` = `ad + toc`（**物理行数**，`inline` 不算进去）：行内切除本来就不删行，
把它混进"保护未删的行"会让恒等式对不上（`dropped.ad` 是 0，保护却记了 1）。
`protected.inline` 单独一个数，只表示"这几行的广告尾巴按你说的没切"。

`samples.ad[]` / `samples.toc[]` / `samples.inline_ad[]` 的每一项都多了 `protected: true|false`，
界面可以直接拿 8 条样例画勾选态；但**要列全量必须读 `dropped_lines`** —— samples 只有 8 条，
第 9 条以后的广告拿 samples 永远勾不到。

**`dropped_lines` 里有正文，必须脱敏**：`--redact` 下每条 `text` 会被换成形状指纹
（`〔长23 中4 西14 空1 符4 #72fdf336〕`），`line` / `kind` / `protected` 原样保留。
这是实装时才补的一处 —— 原先 `redact_report()` 只处理 `samples`，`dropped_lines` 是后加的字段，
漏掉等于 `--redact` 直接失效。

`clean-report.md` 新增 `## 人工调整` 小节，**只在真用了 adjust 时出现**
（保护了行、断开了合并，或**给了行号却没命中**——第三种最需要写进报告，
用户以为保住了一行、实际什么都没发生，只有这里点名他才看得见）；没传 adjust 时
报告与以前一字不差。样例区也**按"删掉的"和
"人工保护留下的"分表**：混在一张「（已删除）」表里，caption 的"共 N 条"会和表格行数
自相矛盾，用户会以为自己保护的那行其实被删了。

### 7.6 与提议的差异（GUI 照实际写）

- 提议里的 `report["protected"] = {...}` → 实际在 **`report["adjust"]["protected"]`**。
  没有做顶层别名：GUI 侧还没写代码，没有兼容负担，同一份信息放两处只会漂移。
- 提议里的 `report["adjust_applied"]` → 实际是 **`report["adjust"]["applied"]`**，
  且多带了 `requested`（用户要了几个）与 `ignored`（哪几个没生效、为什么）。
- 提议里"clean-report.md 加一行「N 处人工调整」" → 实际是一个小节，因为
  保护行、广告/目录的拆分、断开的合并次数是三件不同的事，一行塞不下。

### 7.7 为什么必须重跑、不能在产物上直接改

碎行合并是全局行为（`_merge_fragments`），一行该不该并取决于邻居；在章节树上手工并段会绕过
`_plan_toc_drop` / `_plan_reprint_toc_drop` / `_promote_volume_lines` / `_merge_fragments` /
`_mark_verse` 那一串前置判断（`clean.py:3427-3542` 的调用顺序就是这些判断的顺序，
2026-10-26 订正行号；实装 adjust 后行号又往后挪了一百多行，本轮再订正一次），得到的是一本「规则没跑完」的书。重跑保持「决策在规则层、人工只否决」这个顺序。

**保底方案 B**（直接编辑 `book.json`）**不再需要**：A 方案已落地。B 的代价是恢复被删的行
要靠 `Chapter.start_line` 回原文取行、且丢规则可追溯性（下次重跑还得再修一遍）——
这条仍然成立，所以以后也不该退回 B。

## 8. 封面：九款程序化版式（Calibre 复刻方案已作废）

> 变更记录：本节最初写的是「照抄 Calibre 的四主题 × 五样式」。实测默认封面观感不合用，
> 方案改为九款自研版式。Calibre 的调研结论仍留在 `backups/_research/`，但**不再作为实现依据**。

### 8.1 为什么不做 Calibre 那套

调研把 Calibre 的真实实现摸清了（布局全在 `src/calibre/ebooks/covers.py`；1200×1600 三段
120/80/80px；4 主题各 4 色；5 样式 The Cross / Half and Half / Banner / Ornamental / Blocks；
每次 `random.choice`（:618-619）；超长文字静默丢行（`Block`:168，`max_height = h//3`:622）；
没有可见水印，只有 PNG tEXt :630）。但**照抄它没有意义**，三条理由：

1. **观感**。四主题 × 五样式是「自由组合」，底色和版式互不认识——浅色纸面风压到深色主题上
   就成了一块黑板。新方案改成**版式自带底色约束**（见 §8.4）。
2. **稳定性**。`random.choice` 让同一本书每次重导都换脸。本项目字节可复现是硬设计
   （`build_epub` 的 `ZIP_TIME=(1980,1,1,0,0,0)`、`modified` 取输入 mtime），随机选版式直接打穿这条。
3. **丢字**。Calibre 放不下就**静默丢弃整行**——等于丢书名。新实现一律逐档降字号（0.94 倍），
   降到底仍放不下才截断。

### 8.2 九款版式

| 模板 | 版式 | 底色约束 | 适合 |
|---|---|---|---|
| 章 | 学术横排，双细线收边，右下压一方小印 | 浅 | 通用，什么书都不出错 |
| 简 | 竖排居中，长书名自动分 2–3 栏（右起，中文竖排顺序） | 任意 | 古典、诗词 |
| 框 | 民国出版风：双线内框 + 顶部题签色带 + 红隔线 | 浅 | 公版经典、文集 |
| 对 | 上纸下色块对切，书名压在纸上 | 浅 + 松墨 | 色彩气质强的书 |
| 栏 | 满幅竖界栏，一条白条压住书名 | 浅 | 极简、现代 |
| 碑 | 首字放大成巨淡底纹，900 字重压中，白描方印 | 浅 | 厚重、历史、武侠 |
| 印 | 整张即一方印章，书名竖排为印文 | 底色=强调色 | 气质最独特，挑书 |
| 夜 | 墨底渐变 + 大字距横排，永远深底 | 深 | 悬疑、恐怖 |
| 疏 | 左上角对齐 + 满幅细界栏 + 小印 | 浅 | 最克制 |

| 黛青 | `#E4E8EE` | `#1B2430` | `#35577D` | `#5A6674` | 12.73 | 4.76 |

`mu` 是按 4.5:1 反推出来的；改任何一个颜色都必须重跑对比度校验（§8.5）。

后两套是补的：只有两套浅色时，8 本书实测出现 5 张青瓷，书架糊成一片。四套浅色现在
分在冷暖两端（宣纸暖白 / 赭石沙黄 / 青瓷冷绿 / 黛青冷蓝），深色两套一暖一冷。

### 8.4 自动挑选：模板 × 配色不是自由组合

一键导出必须零决策，但「自由随机组合」会出事故——实测 8 本书跑出来的结果是
《红楼梦》被分到满版金印、《凡人修仙传》的学术纸面压到墨底上成了黑板。所以：

- **先按书名长度筛版式**：≤5 字 `[章 对 框 碑 夜]`；6–9 字 `[章 简 框 碑 疏 夜 对]`；
  ≥10 字 `[简 栏 疏]`。
- **两条池子约束**：`夜` 只进 SHORT/MID（十几个字的大字距横排会糊成一片）；
  `章` 不进 LONG（学术单块版式折成三行就散了）。
- **再按版式筛配色**：纸面五款只配 `宣纸/青瓷/赭石/黛青`；`夜` 只配 `松墨/靛蓝`；
  `对` 配 `宣纸/青瓷/赭石/松墨`（**排除靛蓝**——它的强调色是金色，铺成一整块太张扬）；`简` 任意。
- **`印` 不进自动池**：存在感最强，只作手选的「签名款」。
- 种子：`sha256(书名)` 前 8 位定模板、次 8 位定配色。**同一本书永远同一个样子**。

**边缘分布用 600 个合成书名实测，不拿 8 本书的夹具调参**——8 个样本的抖动会把池子调歪。
实测：章 11.8% 简 17.0% 疏 15.2% 框 12.2% 夜 11.7% 对 11.2% 碑 11.2% 栏 9.8%；
配色 青瓷 22.8% 宣纸 20.2% 赭石 19.2% 黛青 17.5% 松墨 11.2% 靛蓝 9.2%，深色封面合计 20.3%。

第一版有个结构性漏洞：`夜` 一个池都不在，等于「九款版式只有八款可达」，深色封面永远
出不来（浅/深 = 373/27）。把 `夜` 放进 SHORT/MID 后深色占比升到 20%，接近真实书架上
深色封面的比例。

- 已知局限：**单本书的哈希会抖动**。8 本夹具实测 4 本撞上「章」、4 本撞上黛青——
  这是 8 个样本的运气（`sha256` 取模在大样本上均匀，已独立复核）。
  产品侧的出口是「换一个」按钮；**书库级别的均衡不做**，那需要全局状态，
  与「同一本书永远同一个样子」直接冲突。

### 8.5 硬性约束（都是实测踩出来的，写进代码注释）

- **确定性**：54 组（9 模板 × 6 配色）连画两次，PNG 字节完全相同。版式里没有 `random`，
  噪点纹理由 `seed` 派生且点数固定。
- **对比度**：绘制时把 `(字号, 文字色, 当时底色)` 记进 `TEXT_LOG`，事后按 WCAG
  大文本（≥24px）3:1 / 正文 4.5:1 断言。**54 组全部通过，最低 4.71:1**。
  早期版本是在成品图上「按众数猜底色、按分位猜文字色」，在「对」上量到的是空白区域，
  报出 1.04:1 的假警报——**审计必须读绘制现场，不能读成品像素**。
- **PIL alpha 陷阱**：RGBA 画布上 `ImageDraw` 画带 alpha 的颜色是**替换像素**不是叠加，
  存 PNG 转 RGB 时按黑底压平，半透明细线会黑成一大块。所以画布一律 RGB，
  `C(hex, a)` 按当前底色预混合成不透明色。
- **竖排必须右起**：`简` 的多列竖排最初写成 `x0 + ci*colw`（左起），两列以上书名会被读成
  「后半段 + 前半段」——《书Y》读成「险屋的夏天我有一座冒」。`印` 一直
  是对的（`x0 - ci*colw`），改 `简` 时对齐它；作者列也放到标题块左侧（右起读序里作者在书名之后）。
- **不丢字**：`fit()` 逐档 0.94 降字号，永不丢行；`wrap()` 带中文禁则
  （`。，、；：？！）』」》·—…` 不许行首，末行单字回收）。
- **量级**：1200×1600（3:4），单张 47–171KB，129ms（含 PNG optimize 与 §8.9 的底纹）。
- **字体**：`fonts.available_fonts()` 的 Noto Serif SC / Noto Sans SC（就是 EPUB 内嵌那两款）。
  取不到时回退系统宋体/黑体**并在结果页记一条警告**——静默回退会让封面和正文不是同一套字。

### 8.7 顺带补掉一个现存缺口：用户自选封面图

### 8.9 纸质底纹（2026-10-27 实装，自带素材的质感层）

素材是 22 张 PNG，1086×1448（宽高比 0.750，与 1200×1600
画布一致，放大 1.10× 正好铺满）。**这 22 张分成两个族，用途完全不同**：

| 族 | 张数 | 是什么 | 本期怎么用 |
|---|---|---|---|
| A 纹理 | 9 张入库 | paper / grain / ink / metal 各 light+dark，加 cloth_dark | **当质感层铺在底色上**（本小节） |
| B 万能封面预设 | 10 张 | 整幅背景画，景物压在下 1/3 | **不接**（要走"整幅当背景"另一条路径） |
| 图标 | 2 张 | 1254×1254 RGBA | 另见 §9 的 icon_tile 方案 |

**分族的判据不是文件名，是量「上方 60% 横带的标准差」**（书名落在那条带里）：族 A 上带
sd 35–50%，族 B 上带 sd 4.5%–50% 差异极大。质检剔除两张：`cloth_light`（浅底文字带
p05=63，深色字压上去不到 4.5:1）、`light_03`（景物压在上方 60%，与"大字落上方留白"冲突）。

**幅度按 sRGB 色阶步数，不是相对亮度 sd。** 这是本小节最贵的一课：第一版按「相对亮度
sd ≈ 9%」标定，26 个组合全部"合格"，但深底一片死黑 —— 松墨底色 `#15181D` 亮度只有
0.9%，9% 的相对波动换算成 8-bit 色阶不足 1 级。改用色阶步数后 `TEXTURE_AMP = 8` 是
目视标定点：浅底颗粒清晰且大字更实，深底看得见纸的质感但不脏；六套配色下最坏文字对比度
仍 ≥ 11:1（要求 4.5:1）。

**不能只改 `_Canvas.new()`**：九款版式里三款不走它 ——「对」自己建 RGBA 并中途换底两次、
「夜」自己建 RGB 再叠竖向渐变、「印」整张就是强调色底。只改 `new()` 会漏掉这三款
（实测「夜」连调试字段都没被赋值，因为它一次都不调 `new()`）。所以底纹做成独立一步
`paint_base(img, base_rgb=None, region=None) -> bool`，谁建画布谁调；`region` 让「对」的
上下两块各按各自的底色上色。**没有纹理时 `paint_base` 填实色并返回 False** —— 否则
「对」的底部深色块会整块消失（实测过一次 canvas 全白、色块不见）。

**PNG 体积是这一节真正的难点**：平滑纹理与无损压缩天然不兼容。直接铺全分辨率纹理，
同一张封面从 66 KB 涨到 **1035 KB（15 倍）**，`optimize=True` 还要 0.98s/张。逐档实测：

| 纹理处理 | 整张 PNG | 单张耗时 |
|---|---|---|
| 不铺纹理 | 66 KB | 119 ms |
| 全分辨率直接铺 | 1035 KB | 608 ms |
| 缩到 600×800 再放大 | 992 KB | — |
| 缩到 300×400 | 684 KB | — |
| 缩到 150×200 | 438 KB | — |
| **缩到 150×200 → 量化 3 级 → BILINEAR 上采样** | **99 KB** | **129 ms** |

换成 P 模式量化、半调网点都没解决（487 KB / 227 KB，且慢到 2.3s）。真正有效的是
**先量化再放大**：放大后是"大片平坦区 + 少量过渡带"，PNG 才压得下去；先放大再量化是
满屏抖动点，反而压不动。**为什么可以这么狠地降**：纹理只是低频"纸的质感"，高频细节由
`grain()` 程序化噪声负责，素材不必承担高频。

**不用 JPEG**：解码必须跨机器逐字节一致，JPEG 依赖 libjpeg 版本会让成品哈希漂。

**素材入库形态跟着改**：运行时第一步就是缩到工作尺寸，所以入库就存工作尺寸
（150×200 / 3 级）：9 张从 3.09 MB 降到 **19 KB**。原始 1086×1448 在两处有备份
（历史素材目录），随时可重新导出。

**回落链**：「印」映射到 cloth，但 `cloth_light` 被剔除 → 浅底「印」本来一张纹理都拿不到、
就是纯色块（`case_every_template_has_texture` 抓到）。加 `_TEXTURE_FALLBACK`
（grain → paper → ink → metal）按侧回落，映射表不动（深底 `cloth_dark` 是好的，
一张表同时服务明暗两侧，缺哪侧就在哪侧回落）。

验收：54 组全部出图且 `audit=True` 无 `CoverError`；字节确定性「冷缓存 == 热缓存 ==
清缓存后再来」三者逐字节相同（否则用户先点「自动生成」和再点回来会拿到不同的图）。

### 8.10 整幅背景（族 B 十张预设，实装九张，2026-10-27）

族 B 那十张（`light_03` 质检剔除，实装九张）**不是纹理，是整幅背景画**：画作压在一条边上
（下 1/3、左下角、右上角），其余是大片留白。它们不能走 §8.9 那条"给纯色底加质感"的
路 —— 那里文字落在空白中央，这里文字必须落进**画作留出来的那块地方**。

**落点是量出来的，不是猜的。** 把每张图切成 6×6 网格算每格 `mean/sd`，sd 小的格就是
干净留白（笔触会让 sd 跳到 15 以上）。九张全部有干净的上方 50%；只有 `dark_03` 的松枝
伸到右上角（行0列4-5、行1列3-4，sd 20–30.7），所以它 `align=left` 且 `maxw=0.55`。
`light_05` / `dark_05` 通体柔和（sd ≤ 9.4），可用整张，文字居中。

| 素材 | 界面名 | 深底 | 落点 | 对齐 | 宽度上限 |
|---|---|---|---|---|---|
| `light_01` | 远山 | | top | left | 0.62 |
| `light_02` | 海平线 | | top | center | 0.68 |
| `light_04` | 梅枝 | | top | left | 0.60 |
| `light_05` | 云雾 | | center | center | 0.66 |
| `dark_01` | 山影 | ● | top | center | 0.66 |
| `dark_02` | 水波 | ● | top | left | 0.62 |
| `dark_03` | 松枝 | ● | top | left | **0.55** |
| `dark_04` | 夜梅 | ● | top | center | 0.62 |
| `dark_05` | 暗云 | ● | center | center | 0.66 |

`label` 是给界面看的名字：素材文件名（`light_01`）是工程记号，不该出现在用户眼前。
文字色不另配 —— 深底用宣纸白 `#F1EFE8`、浅底用墨 `#1D1E1E`，与六套配色里的"墨/纸"
同一对，跨主题一致。

**位深是目视标定出来的。** 5bit（32 级）与原图肉眼无差；**4bit 不可用** —— `light_01`
的暖奶油色被量化成**偏黄绿**（色相偏移，不只是色带），`dark_05` 出现块状台阶。
JPEG 一律排除（解码依赖 libjpeg 版本会让成品哈希漂，违反 §8.5 的字节可复现）。

体积逐档实测（同一张 1200×1600 成品）：

| 处理 | `light_01` | `light_02` | `dark_03` |
|---|---|---|---|
| 原始 | 1940 KB | 1911 KB | 1720 KB |
| 5bit | 558 KB | 608 KB | 463 KB |
| blur0.6 + 5bit | 538 KB | 593 KB | 472 KB |
| **blur1.0 + 5bit** | **368 KB** | **453 KB** | **346 KB** |
| blur1.0 + 4bit | 101 KB | 415 KB | 239 KB |

选 **`_BG_BLUR = 1.0` + `_BG_LEVELS = 32`**（按 1200 宽定标）：9 张成品 316–462 KB，
单张 496–830 ms。比程序化封面的 99 KB / 129 ms 慢且大，**所以这是可选模式**，
默认仍是"无封面"。

**入库形态**：600×800 RGB 5bit，9 张合计 1156 KB（单张 107–146 KB）。600×800 正好是
1200×1600 的一半，2× 放大像素边界对齐，不产生 LANCZOS 振铃。

**新素材从哪来。** 这九张**本身就都是 AI 生成的**（族 B 是整套预设背景，
那 22 张也是 AI 出的）。要新底图，用本机的 skill `qwen-image-turbo-t2i` 离线出
（Qwen-Image-2.1-Turbo / sd.cpp / Vulkan，RX 7700 XT 12GB）。
这是常规素材工序，不是例外路径 —— 出来的 PNG 与这九张没有区别，照样要按本节这套量落点、
降位深、写元数据。§1「不做 AI 生图封面」管的是**产品功能**（界面里没有生成按钮），
不管素材怎么来，两件事别混。调用方式与实测数据见 README「开发」章的「素材：本地出图」。

**★ 缓存必须返回副本。** `_load_background` 若直接返回缓存对象，`_draw_background_cover`
会在这张图上画字 —— 第二次画出来是"上一张的字 + 这一张的字"，连画两次字节不同，
第三次直接抛对比度不足（实测）。`case_background_cache_not_polluted` 用「A → B → A」
序列钉住这一条。

**对比度审计量的是文字块区域的实际最坏像素**，不是常数底色：背景画在一块区域里可能有
明暗过渡，深色字怕最暗的像素、浅色字怕最亮的。故意把 `dark=True` 套在亮图上，审计会
正确抛 `CoverError: 150px 文字与底色对比 2.42:1，低于 3.0:1`。

**标题字号先定行数再定字号**：只要求"≤3 行"会挑到 150px，把 "The Great Gatsby"
拆成三行每行一个词（实测）。改成"在所有候选里取行数最少那一档中最大的字号"。

接口（§8.6 的追加）：

| 名字 | 说明 |
|---|---|
| `BACKGROUNDS` | 九张的元数据：`label` / `dark` / `zone` / `align` / `maxw` |
| `background_names()` | 本机真正可用的（素材缺了就少一张） |
| `background_label(name)` | 界面显示名，认不出来回原名 |
| `pick_background(title, step=0)` | 确定性起点（按书名 sha256 取模） |
| `next_background(name, step=1)` | 「换一个」轮转；非法起点回 `names[0]` 不抛错 |
| `make_cover(..., background=...)` | 给了背景就忽略 template/theme |

验收：9 张 × 两遍字节全同；9 条变异（去掉副本、去量化、去平滑、改时间起点、
非法起点抛错、label 透传原名、非法名不报错、有背景仍看 template、正式产物用预览尺寸）
**13/13 全抓住**。

- **`SPECPATH` 是 spec 文件所在目录**（本项目 spec 在 `build/`，所以项目根是 `Path(SPECPATH).parent`，
  只取一次）。写成 `.parent.parent` 会指到上一级目录，报 `script '...\gui\launcher.py' not found`。

  唯一的解析点收在 `gui/app.py:_resource()`，`launcher` 自检也调它，保证两处说的是同一份路径。
- fontTools 缺失时 `plan_fonts` 返回 None → 不内嵌字体 + 一条警告，与 CLI 一致，GUI 不额外报错。
- 有些机器上大量路径被重定向（桌面、TEMP 都可能被搬到别的盘）：默认目录一律用
  `[Environment]`/`Path.home()` 之类的现取方式，禁止硬拼 `%USERPROFILE%` 路径。
  **日志同理不写 TEMP** —— 用户会去 exe 旁边找，`_log_dir()` 在 frozen 时返回 exe 所在目录。
- **`--selftest`（2026-10-27 加）**：`huoban.exe --selftest` 不开窗口，把 version / imports /
  resources / pipeline 四步各跑一遍（pipeline 是真造一本 GBK 脏书走完清洗→打包），
  结果写 `huoban-selftest.json`（exe 旁边）并返回 0/1。
  没有它，`console=False` 的 exe 双击没反应时**没有任何地方**能说明断在哪一层。

> 四个岔路已定：**插图四档分流** / **新增 `caption` 字段** / **多看式排版做成预设** / **分片按「相邻 + 同主干」合并**。

### 12.1 定位：重建结构，不是换皮

| 做法 | 代价 | 结论 |
|---|---|---|
| 换皮：只替换 `main.css` 与字体 | 零信息损失，约 200 行 | 否 |
| 重排：走章节树重新决定每段是什么 | 丢字符级格式（加粗/斜体/ruby） | **是** |

真正的收益不是「多支持一个格式」，而是**多一个进料口，共用同一条产线**：产物仍是章节树 JSON，
之后的排版、字体子集、封面、元数据、字节可复现全部免费复用。
GUI **不用为导入新增视图**（2026-11-06 订正：原文写「五个视图一个都不用新增」，视图数后来长到 8 个；
结论不变 —— 导入这条线确实一屏都没加）。

**明确不支持**：带 DRM 的 EPUB（直接报错）；固定版式 pre-paginated（本机 351 本实测 0 本，
遇到报「这本是固定版式，无法重排」）。

### 12.2 插图排版：四档分流（Q1 定案）

死灵之书 45 张插图宽高比从 **0.69 到 4.08**，跨度六倍。照抄它那个一刀切的 `width:50%`，
`32.jpg`（864×212）、`43.jpg`（1156×376）会变成很细的横条，图上的字全糊。实测分布与对策：

| 宽高比 | 张数 | 容器宽 | 理由 |
|---|---|---|---|
| < 0.85 竖图 | 22（49%） | 60% | 画册类插图，比正文半栏略宽就有存在感 |
| 0.85 – 1.6 方图 | 17（38%） | 70% | 方图在半栏里显小 |
| 1.6 – 2.5 宽横 | 3（7%） | 90% | 横向构图，宽度不够细节就糊 |
| > 2.5 极端横条 | 3（7%） | 100% | 塞 50% 会变成一条线 |

配套两条硬约束：

1. 图片一律 `max-width:100%` + `max-height:95vh`，竖长图不会顶破一屏。
2. **图片位置原样保留，不搬去章末。** 死灵之书那 43 张在故事末尾是原书编排（距文末 233–941 字符，
   多数约 245），不是通例；`Section01-052.html` 的符咒图就在长文中段（距文末 27,689）。

图说的样式照它：楷体 `0.9em`、居中、上间距 `1em`、无边框无底色 —— 只靠字体和正文拉开。

### 12.3 数据契约 v2（Q2 定案：新增 `caption`）

```json
{
  "kind": "image",
  "text": "img003.jpg",
  "caption": "《书甲》的手稿。",
  "width": 927,
  "height": 1265
}
```

| 字段 | 说明 | 何时写 |
|---|---|---|
| `text` | 图片文件名；白名单扩展名，不许含 `/` 与 `..` | 必有 |
| `caption` | 图说，可空 | 原文有图说才写（死灵之书 45 张里 41 张有） |
| `width` / `height` | 像素尺寸，四档分流靠它算宽高比 | 必有 |

**兼容代价**：`SCHEMA_VERSION` 1 → 2；`model.py` 的 `from_dict` 版本检查现在只比主段
（`version.split(".")[0]`，不等就 `raise ValueError`），必须同时改成接受 `{1, 2}`，
否则所有旧 `book.json` 读不进来。`to_dict` 只在 `kind="image"` 时写这三个新字段，
旧章节树重新序列化后字节不变。`validate()` 补一条：`kind="image"` 时 `text` 必须是白名单扩展名；
`caption` 非空但 `kind` 不是 `image` 时报警告。`stats()` 跳过 `image` 段（现在会把文件名当字数算）。

### 12.3b 数据契约 v2 追加：`anchor` 与 `refs`（弹注）

```json
{
  "kind": "body",
  "text": "正文开始继续。",
  "anchor": "noteref_1",
  "refs": [{"at": 4, "note": "rearnote_1", "label": "[1]"}]
}
```

| 字段 | 说明 | 何时写 |
|---|---|---|
| `anchor` | 本段在原书里的 HTML id（注释段靠它被正文指到） | 原书有 id 才写 |
| `refs[].at` | "插在第 at 个字符之前"（0 基，`text` 里**不含** `label`） | — |
| `refs[].note` | 目标段的 `anchor` | — |
| `refs[].label` | 显示文字（`[1]` 这类） | — |

两个字段都只在非空时写进 JSON，理由与 `caption` 相同：v1 旧文件重新序列化必须逐字节不变。
`validate()` 补四条：`anchor` / `refs[].note` 必须是安全 id（白名单 `^[A-Za-z0-9_.:-]+$`，
因为它们会原样拼进 xhtml 属性）、`at` 必须是非负整数且不超过本段长度。

### 12.4 尺寸必须在解析时拿到，不能让打包层读图

Pillow 在本项目里是**可选依赖**（照 `fonts.py:42-49` 的 `try/except ImportError` 降级范式），
而 `build_epub` 是纯函数、不写盘。让它依赖 Pillow 会把「没装 Pillow 也能出 EPUB」这条破掉。

所以解析时用**标准库**读图头拿宽高，几十行：PNG 读 IHDR（偏移 16–23 的 big-endian 两段），
JPEG 扫 SOF0/SOF2 段。GIF 同理（逻辑屏幕描述符 6–9 字节）。读不出来的（损坏、格式不认）
记 `width=height=0`，排版时按「方图 70%」兜底并记一条警告。

### 12.5 三类图片判定（都是实测踩出来的）

**① 装饰图 —— 必须丢弃。** 宰执天下 2241 个章节文件每个顶部都有一张 `logo.png`（823 KB）；
死灵之书 `logo2.png` 引用 79 次、`note.png` 引用 120 次。若按「保留所有 `<img>`」实现，
重排后每章开头都会多一张装饰图。判据：**同一图全书引用次数 > 阈值**判装饰，丢弃并记报告。

阈值 = **10**（2026-10-28 实测定标，原来是"暂定 5"）。定标样本：349 本真 EPUB 里 91 本带图，
共 3,157 张图次引用 —— 引用 1 次 2,951 张（93.5%）、2 次 107 张、3–8 次合计仅 35 张、
**9 与 10 是空的**、家具图从 11 次起跳（11/15/16/18 … 直到 2,241 与 3,386）。

### 12.6 脚注

多看私有扩展（宰执天下 114 个文件 503 处，死灵之书 120 处）：

```html
<!-- 引用处：图标不是数字 -->
<sup><a class="duokan-footnote" href="#fn12" id="fnref12"><img src="../Images/note.png"/></a></sup>
<!-- 章末正文 -->
<ol class="duokan-footnote-content"><li class="duokan-footnote-item" id="fn12">此是史实。</li></ol>
```

对策：`li.duokan-footnote-item` 的文字 → 已有的 `kind="note"`；引用处图标丢弃。
通用写法 `epub:type="footnote|endnote|rearnote"` 的 `aside` 同样映射 `kind="note"`。

**Calibre 的写法没有 `epub:` 前缀**（实测样本：`noteref` 7104 次，`footnote` 与
`epub:type` 全 0）：

```html
<!-- 正文处 -->
<p>……正文<a id="noteref_1" type="noteref" href="part0178_split_000.html#rearnote_1">[1]</a>继续。</p>
<!-- 注释集中在一章 -->
<section type="rearnotes"><aside id="rearnote_1" type="rearnote">
  <p><a type="noteref" href="part0007.html#noteref_1">[1]</a>祖斩白蛇。</p></aside></section>
```

三层都要做，缺一层弹注就不工作：

1. **认类型**：判据统一走 `_type_words`（`epub:type` 与无前缀 `type` 拼起来看）。
   **注释语义常写在容器上、文字在子元素里** —— `<div type="footnote"><p>注文</p></div>`
   里那个 `p` 自己什么标记都没有，只看本帧属性会整批漏掉，所以帧上带 `is_note_box`，
   收帧时只要祖先帧（含本帧）是注释容器，文字就按 `note` 算。
2. **保关系**：解析期用哨兵 `\x01N\x02` 占位（解析时还不知道清洗后字符偏移会变），
   整篇解析完再算真实偏移 → `Paragraph.refs`。`<a>` 的 `href` 片段存成 `note`。
   **跨文件的落点先保留**：Calibre 把全书注释集中到"注释"一章，引用和落点在两个
   xhtml 里；单篇解析看不见对方，只有全书锚点表建好才能裁决 → `_finalize_refs()`
   在 `read_epub` 组装完 Book 后跑一遍，找不到落点的把 `label` 还原回正文（不留死链接）。
   例外：`note` 段开头（偏移 0）的那条反向链接直接丢掉 —— 它是注释自己的编号，
   正文那边已有指过来的链接，留着就是注释开头的多余 `[1]`。
3. **渲出去**：正文 `<a class="noteref" epub:type="noteref" href="chap0007.xhtml#id">[1]</a>`，
   落点 `<p class="note" id="..." epub:type="footnote">`。`epub:type="footnote"` 是
   阅读器判断"这是条注、该弹窗"的依据，缺了它 noteref 只是普通跳转。
   **href 必须写对文件**：注释在别的章节里时只写 `#id` 会跳到当前章一个不存在的锚点，
   所以渲染前先建"锚点 → 文件"表，逐文档生成相对链接（章节文件同在 `Text/`，
   用文件名即可）。全书都找不到落点时只留文字。

**为什么 note 段落渲成 `<p class="note">` 而不是 `<note>`**：`_ELEMENT_BY_KIND` 的第二项
才是 class，tag 必须是合法 xhtml 元素。同一类错误曾出现在书名页短行上
（渲成 `<front-title>`，回读时被当成行内文本吞进相邻段落，死灵之书回环 4505→4491 段），
已修正为 `<p class="front-title">`。

### 12.7 章节切分

- **章节边界的权威来源是 NCX / nav**，不是正文里的标题文字。
- 宰执天下：2250 个 navPoint，深度分布 `{0:1, 1:10, 2:2240}` —— 第 1 层 10 个是「制作说明 / 代序 /
  内容简介 + 7 个卷标题」，第 2 层 2240 个是章。映射：卷 → `Chapter.level=2`，章 → `level=1`。
- **分片合并（Q4 定案：合并，按「相邻 + 同主干」）**。宰执天下实测：2250 个 navPoint 里 2240 个是章，
  七卷 —— 前六卷每卷只有 48 个章号但条目 136~613 条（每章被切成 2~80 片，最多的一章「第四十八章
  时来忽睹红日低」切了 80 片），第七卷 329 章几乎不切片。**两种编排并存**，所以任何全局规则都不成立：

  | 做法 | 结果 | 判定 |
  |---|---|---|
  | 不合并 | 2240 章 | 目录满屏（上）（下）（一）（二） |
  | 按章号合并 | 617 章 | **错**：同一卷「第四十八章」出现 14 次但标题全不同，按号会把无关内容粘一起 |
  | 按「相邻 + 同主干」合并 | **620 章** | 对。285 组被合并，620 个主干无一重名，零歧义 |

  主干判据：去掉尾部 `（上）（中）（下）（全）（续）（一）…（十一）` 后相等，**且必须相邻**；
  不相邻的同名不合并（实测主干重复数 0）。合并后章节树是 620 章，正文里不留分片标记。
  报告里必须报一行「合并 285 组：2240 片 → 620 章」（铁律 2：改了什么要看得见）。

  这条不是宰执天下独有：**多看/掌阅系的制作工具普遍这么切片**，所以它是导入器的默认行为，不做开关。
- **隐藏标题**：`<h1 style="display:none">内容简介</h1>` 不识别就会把「内容简介」当章节名。
- 标题有四种形态，含 `<h2 class="head"><b>第一章</b><br/> 劫后梦醒世事更</h2>`；
  卷标题把完整标题存在 `title` 属性里、内部用 `div`+`span` 拆行：
  `<h1 class="vol-title" title="第一卷 初六之卷——塞上枕戈"><div><span>初六之卷</span><br/> 塞上枕戈</div></h1>`。
- 前附（版权页、扉页、序、译序、制作说明）归 `front_matter`；目录页丢弃。

### 12.11 349 本真池跑出来的两个静默缺陷（2026-10-28）

两条都不是"导入会失败"，而是"导入成功但结果不对" —— 这类问题只有把样本量从
1 本提到几百本才会现形，所以这一节记的是**判据**，不是代码。

**缺陷 A：`<p>` 写的章标题回声进正文。**
TXT 改出来的 EPUB 十有八九把章标题写成 `<p>` 而不是 `<h1>`。
`_drop_duplicate_heading` 原来只检查 heading 块，于是每一章正文里都自带一段与目录
逐字相同的标题，成品就是"h1 章标题 + 一模一样的正文段"上下贴着（合成样本里 28 本
全中；真池 346 本里命中 **21 本**，最多一本 177 段）。
修法是在原规则前面加一条更严的：**章首第一个非空文本块，强归一后完全等于目录标题 → 删**。
只认章首、只认完全相等，所以吃不掉正常句子。
取证：逐段核对 21 本里被删的每一段是否等于该章标题 —— **454 段全部等于，0 段例外**
（`backups/epub-corpus-20261028/verify_dedup.py`）。字数最多的一本掉 2.98%，是标题行的长度 × 章数。

**缺陷 B：一个文档被多个目录节点共享时，文档开头漏进上一章。**
`_split_positions` 的均分兜底按 `run+1` 段切，第一个节点从"让出开头一段"开始算。
那一段不掉进本节点、也不掉进前言，而是由 `_emit(items[:positions[0]])` 掉进
**上一章的尾巴**。真池 194 本里命中 **414 次**，绝大多数只漏 1 段（通常就是章标题那一行）。
改成：这一段是文档开头（前面没有已知锚点）时按 `run` 段切，首节点从 0 算起。
命中数 414 → **0**（`probe_split_leak.py`，只给 `_split_positions` 装只读探针，不改产物）。

**已知代价（如实记，没修）**：B 修好后，"这条目录条目是目录页、整段丢弃"那条**老**分支
会连带吞掉它所在文档的第一段——真池 8 本技术文档共 28 段（1–23 字的节标题）。
`toc_dropped` 计数前后一致，说明这是既有行为被放宽一格，不是新缺陷：这些书本来就是
整本塞在一个 xhtml 里、锚点大面积丢失的形态。要修得先回答"目录页节点该不该吞掉文档开头"，
本轮没定这个判据，所以不动。

**判据小结**：导入这条线的验收不能只看"跑通了没"。要同时看
①账单数 = 磁盘文件数、②章节树引用的图必然在盘上、③回环第 2/3 遍逐段相同、
④回环不丢段、⑤**每一段的删除都能说出它等于什么** —— ⑤ 是这一轮新加的，
因为 A、B 两个缺陷都恰好满足前四条却把内容放错了地方。
