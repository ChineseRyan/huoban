# 设计管理办法

本文只说流程，管一颗**设计需求**从「想改」走到「验收、登记、归档」。
三件事各归各处，别混：

- 界面**做成什么样**的权威：`docs/gui-design.md`；
- 设计资产**有什么、放哪、怎么登记**：`docs/design-assets.md`；
- 对外**宣传素材**的规矩：私有库 `huoban-notes` 的 `promo/`（`promo-design.md` / `promo-assets.md`）。

本文不重复上面任何一份，只在流程上规定「什么时候必须去那里办」。

文中的角色：**开发者**（与肥鱼对话、拍板的人）；**管家肥鱼**（领队，只做统筹与转达）；
**需求肥鱼**（维护 `todo/`）；**UI设计肥鱼**（出稿与 `gui/ui.html` 落地）；
**编码肥鱼**（业务代码、接口）；**文档肥鱼**（文档维护）。称呼一律用这些名字，
「设计 / DEV / DOC / TODO」只是角色标签，不写进正文（2026-11-14 开发者定）。

## 什么是设计需求（和 bug 的边界）

- **用户能感知到的「错误行为」是 bug**，走 `docs/bugfix-workflow.md`：该出的书没出、
  按钮点了没反应、字压出屏幕。
- **能跑，但观感、交互、信息组织要更好**，是设计需求，走本文：按钮不够醒目、
  错误页文案不像人话、关于页想换布局、某屏想逐屏重审。
- 拿不准算哪类：先问开发者定，不自己归类。两条流程的验收方式不同
  （bug 先钉回归用例，设计靠开发者逐屏判），归错类就是两头空跑。

## 设计需求从哪来、怎么记

**入口只有一条：开发者说、需求肥鱼记。**

1. 开发者直接把设计需求交给 **需求肥鱼**，由它记录进 `todo/`——
   条目怎么写按 `todo/README.md` 的既有规矩办，本文不越权。
2. UI设计肥鱼、编码肥鱼 干活时自己发现的、竞品或调研引出的，**先报开发者**，
   由开发者决定要不要交给 需求肥鱼记录。**自己不往 `todo/` 里塞，也不自行开工。**
3. `todo/` 只有 需求肥鱼改；其他角色读到缺漏或不清楚的地方，报开发者，不动文件。

设计需求条目与 bug 条目同处 `todo/` 目录，按版本分文件（长期条目在 `长期计划.md`）；
在哪个版本落地由开发者定，版本口径见 `AGENTS.md` 的「版本更新原则」——与 bug 同一套。

设计需求条目标题带**「【设计】」前缀**（2026-11-14 开发者定、需求肥鱼定格式），
与 bug 条目、技术需求同处 `todo/` 目录，靠前缀区分；其他角色搜「【设计】」就能找齐。

## 设计阶段怎么启动

设计阶段**由开发者启动**：开发者点名 UI设计肥鱼 去查 `todo/` 中属于当前目标的设计需求条目，
UI设计肥鱼 才正式进入设计阶段。

- **UI设计肥鱼 不自行从 `todo/` 挑活开工**，也不把「看到了」当成「轮到我了」。
- 开工依据是条目本身。现有设计条目沿用 `todo/` 条目同一套字段，多两样（设计稿与版式），
  UI设计肥鱼 开工前逐项核对，缺一项就报开发者（由 需求肥鱼补条目），不猜着做：
  1. **现象或来由**、**口径（带日期）**；
  2. **候选设计稿与沿革**：稿子路径 + 哪版作废、谁哪天定的；
     设计稿本体在 `designs/`，条目里是**引用关系**，不抄稿子正文；
  3. **版式规格**：逐项尺寸 / 色值 / 变量；
  4. **资产**：新增或替换哪些、放哪、要登记到 `docs/design-assets.md`；
  5. **验收**：能实测——截图比对、点一遍、跑哪个测试；
  6. **开工前待确认**；
  7. **范围**（即「不能动的」）：如不重画 logo、不动版本号、不动清洗、打包与输入文件。
- 条目里没定的事，沿用条目的「开工前待确认」写法列出来（需求肥鱼 的既有格式），
  动工前必须问过，不许 AI 自己拍。

## 出稿：三稿对比（含豁免）

- **默认出 3 稿**：大多数情况下都出三稿（整屏重做、新屏、新交互，乃至一般改动），
  一页并列同一个内容（同一屏、同一状态）供开发者对比；不把三稿拆成三个文件让人来回切换。
- **例外只由开发者开**：开发者明确说「这次不用三稿」时，按他要求出（通常是 1 稿 +
  改动前后对比图）。职责窗口不自己给自己豁免。
- 稿里内容要真实：用真界面文案与真实状态，不造示意图、不编数据、不放真实用户的图或书。
- **稿放哪**：
  - 评判用的 HTML 原型进 `designs/`（入库）——一页并列多稿，
    命名沿用关于页先例（`主题-方向稿.html` / `主题-final-vN.html`）；
  - 候选现场与中间产物留在 `design/`、`_shot/`（不入库，见 `.gitignore`）；
    `design/03-终稿` 只由开发者挪，AI 不动。
- 旧稿入库就是证据链：被否也留，别删；真要清按回收站走。

## 开发者评判

- 开发者逐条给意见（三梯队列法可用：必改 / 该改 / 可改）；判定结果报给开发者，
  由 需求肥鱼落进 `todo/` 条目。
- AI 不代判、不预设选项；「我建议 X」不许写成「定为 X」。
- 不过就出一版**对照稿**（v2），只改判过的点，不顺手重构；对照稿同样一页并列
  （深浅两态并列也行，关于页 v2 即此形态）。
- 判完要记一笔：改了什么、哪些意见没采纳、为什么。

## 定稿留痕

- 「定稿」= 开发者明确说出**以哪份稿为准**。没这句话，一律按候选稿算。
- 留痕三处：
  1. 报给开发者，由 需求肥鱼在 `todo/` 条目上写「以 Y 稿为准」与在哪个版本落地；
  2. `docs/design-assets.md` 的「设计稿」一节补一行（哪份、什么状态）；
  3. 决策笔记照 `docs/notes/` 的 README「新增一篇的判据」一节当场判——
     命中「改判定规则 / 增删依赖例外 / 实现细节被实测推翻」必写；
     其余看「不写的话，下次开新会话最可能做出什么蠢事」。
     汇报里写明一行 `决策笔记：写 / 不写 + 一句理由`，不许默默跳过。

## 落地与验收

- **落地分工（2026-11-14 开发者定；UI设计肥鱼 与编码肥鱼 书面核对两轮，无遗留异议）**：
  - **UI设计肥鱼** 管 `gui/ui.html` 的全部：DOM、CSS、动效、文案、事件监听；
    含首屏拖拽的 dragenter/dragover/drop/dragend 状态判定与分类纯函数、drop 后的
    状态保持与兜底定时器、contextmenu 菜单渲染、关于页外链按钮的
    `preventDefault()` / `stopPropagation()`。断言同归属：`tests/test_gui.py` 的
    「界面（`gui/ui.html`）的静态不变量」一节 + `tools/ui_resize_check.js`
    八尺寸回归；谁动 `ui.html` 谁改这些断言，先红后绿。
  - **编码肥鱼** 管 `huoban/`、`gui/api.py`（全部 js_api 方法）、`gui/app.py`
    （窗口、`_register_drop`、`_dropped_paths`、`__onDropPath` 派发与载荷格式、
    `_debug()` 开关）、CLI、测试与打包。
  - **唯一交界是 js_api 契约**：UI 提需求，每个方法写清五件——方法名 / 入参 /
    返回字段 / 失败表示 / 必需或可缺省；编码肥鱼实现，只返回数据不 print。
    失败表示沿用现状：返回 dict 带 `error` 字段，不抛异常；可缺省的方法要写清
    界面降级动作（先例：`import_excerpt` 在 `ui.html` 有 `?:` 守卫）。
    现役方法清单以 `gui/api.py` 为准；契约五件套的草表由 UI设计肥鱼 与编码肥鱼 补齐。
  - `__onDropPath` 载荷格式由编码肥鱼定，暂不改（仍单个路径字符串），要改先改条目。
  - 硬约束：不许为了让 input 有右键把全局右键打开——右键 / 快捷键 / DevTools
    是同一个 `_debug()` 开关，归编码肥鱼管。
- 验收缺一不算完：
  1. 开发者逐屏验收，明确说没问题；
  2. 八档窗口尺寸回归：`node tools/ui_resize_check.js <页面 URL>`，看末行
     「✓ 8 个尺寸全过」。
     **必须同时看两件事，缺一条这个结论就不成立**：
     - **URL 不能省**。脚本不带 URL 时一档都不跑，却照样打印「✓ 0 个尺寸全过」。
     - **每档的地标数不能是 0**。页面没打开、地址写错、选择器全对不上时，
       脚本照样打印 8 档全过——判定逻辑只报「发现问题」，不报「没测到东西」。
       所以末行「全过」之外，还要确认每档括号里的地标数不是 0（首屏现在是 2 个）。
     地址写 `file:///` 加 `gui/ui.html` 的绝对路径；浏览器不在默认安装位置时，
     用 `CHROME` 环境变量指到本机的 Chrome 内核可执行文件（脚本文件头有说明）。
  3. `python -B tests/test_gui.py` 全绿；
  4. `python -B tools/smoke_test.py` 全绿。
- 发布关口（逐个跑 `tests/`、`python -B tools/smoke_test.py`、PyInstaller 测试包与 sha256、
  `CHANGELOG.md`）归编码肥鱼；这是关口，不构成 `ui.html` 的所有权。
- **没经过第 1 条，不算定稿**；测试全绿只说明没弄坏别的。

## 设计资产同步

- 落地若**新增或替换**资产（图标、底纹、背景、印面、模板图等）：
  成品进 `gui/assets/` 对应子目录，**母版一并入库存档**，并在 `docs/design-assets.md`
  登记一行——登记规矩在那里，本文不重抄，只要求「做到」。
- 三种形态各归各处，别混：
  - **评判稿 / 定稿稿** → `designs/`（入库）；
  - **候选现场** → `design/`（不入库，`03-终稿` 归开发者）；
  - **截图与中间产物** → `_shot/`（不入库）。
- 宣传侧只从母库取真身（见 `promo-design.md` 的「总则」一节）；设计这边要保证母库
  始终登记齐全、可取——**资产没登记，等于对外宣传也没有真身可用**。

## 归档

- 条目完成、验收、发版后：从 `todo/` 移除，按版本归档到私有库 `huoban-notes`
  的 `todo/`（`archive-<版本>.md`）。移除与归档由写条目的人（需求肥鱼）做，同 bug 流程。
- 定稿稿留在 `designs/`；候选与现场按上面的入不入库规矩就地留存，不搬进 `gui/assets/`。

## 不许做的事

- 不擅自替开发者定视觉方向、版本号或排期。
- 不跳过对比稿直接落地（豁免只按「出稿：三稿对比（含豁免）」一节的口径）。
- 不在没登记的情况下新增/替换 `gui/assets/` 里的成品。
- 没验收就说「定稿」；测试没过就说「落地完成」。
- 把设计需求当 bug 改，或把 bug 当设计需求「顺手美化」。
- 公开仓库与设计稿里不出现站点名、渠道名、公众号名这类细节。
